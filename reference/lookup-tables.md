# Довідники (lookup tables)

Хардблок і мінімум правил уже в `core.md` (розділ «Обов'язковий порядок на старті роботи з проєктом», крок 3, і «Наскрізні правила»), завантажується завжди. Цей файл — повні схеми, три ступені наповнення, словник типів позицій, процес верифікації/xlsx-циклу і технічні пастки Mixpanel.

Два довідники, кожен зі своїм ключем і призначенням.

## products_crm — ключ `product_crm_id`

Прив'язується до замовлень і реклами (`order_item_snapshot`, `ad_item_snapshot`).

| Колонка | Хто заповнює |
|---|---|
| `product_crm_id` — ключ | з даних |
| Rozetka ID | з `ad_item_snapshot` або зіставлення |
| Джерело | коротке зрозуміле пояснення, звідки взято Rozetka ID (див. нижче) |
| Точність (%) | число 0-100, визначає ступінь наповнення — фарбує рядок (див. «Кольори рядків») |
| Посилання на товар | `url`/`href` з подій позицій/залишків цього ж `rozetka_id`, якщо він там траплявся (**в `ad_item_snapshot` посилання немає**) |
| Коротка назва | заготовка з даних, людина править |
| Нормалізована категорія | людина |
| Тип позиції | людина, здогадка попередньо заповнена (див. нижче) |
| Статус | людина: перевірено / не перевірено / виведено з асортименту |
| Посилання CRM | за шаблоном з конфігу (business context) |

**Базовий набір рядків — усі `product_crm_id`, що зустрічались у `order_item_snapshot`** (тобто реально продавались), а не тільки ті, що вдалось зв'язати з Rozetka. Товар без визначеного Rozetka ID усе одно потрапляє в чернетку рядком — з порожньою колонкою Rozetka ID, на ручне дозаповнення. Товари, що є лише в `ad_item_snapshot`/сканері позицій, але жодного разу не продавались — у цю таблицю не потрапляють, вона прив'язана саме до продажів.

Ключ — `product_crm_id`, бо він унікальний і **незмінний**. Одна картка Rozetka може відповідати кільком товарам у CRM (різні постачальники) — тоді `rozetka_id` просто повторюється в звичайній колонці, а не в ключі. Якщо картку перепривʼязали до іншого SKU — міняється тільки одна клітинка `Rozetka ID`, ключ лишається, ручна робота не втрачається.

## products_rozetka — ключ `rozetka_id`

Прив'язується до позицій і залишків, включно з конкурентами (`product_position_snapshot`, `extra_product_position_snapshot`, `stock_snapshot`).

| Колонка | Хто заповнює |
|---|---|
| `rozetka_id` — ключ | з даних |
| Джерело | коротке зрозуміле пояснення, звідки взято товар (див. нижче) |
| Точність (%) | число 0-100, визначає надійність джерела — фарбує рядок (див. «Кольори рядків») |
| Назва картки | з `name` |
| Посилання на товар | готове поле `url` (позиції/extra) або `href` (`stock_snapshot` — інша назва поля!), не будувати вручну |
| Продавець | з `seller` |
| Свій / конкурент | попередньо за пріоритетом джерела (див. нижче), підтверджує людина |
| Конкурент для (rozetka_id свого товару) | похідне зі зіставлення `search_query`, тільки для рядків-конкурентів; людина перевіряє/доповнює |
| Нормалізована категорія | людина, за бажанням |
| Статус | людина: перевірено / не перевірено / неактуально (картка довго не трапляється в даних) |
| Примітка | людина, за бажанням |

Колонка «свій/конкурент» — страховка на випадок, коли `seller` порожній чи ненадійний. Колонка «Статус» — той самий верифікаційний workflow, що й у `products_crm` (нові рядки завжди «не перевірено», кольори в xlsx-шаблоні ті самі), просто без «виведено з асортименту» — тут це не «свій товар знято», а «картка довго не з'являється в даних».

**«Конкурент для» — не гарантовано 1:1, заповнювати обережно.** Ні `product_position_snapshot`, ні `extra_product_position_snapshot` не несуть прямого поля «чий це конкурент» — точного зв'язку в самих подіях немає. Похідний спосіб: зіставити `search_query` (і бажано `scan_type`) конкурента з `extra_product_position_snapshot` із `search_query` власних товарів у `product_position_snapshot` того самого сканування. Один конкурент може траплятись у видачі кількох різних власних товарів (спільний пошуковий запит) — тоді перелічити всі `rozetka_id` через кому, а не обирати один довільно. Якщо збігів декілька і незрозуміло, який основний, — позначити в «Примітці» і лишити на розсуд людини, а не вгадувати. Порожньо для рядків, де «Свій / конкурент» = «Свій».

Створюється не на першому запуску, а коли вперше з'являться події позицій.

## Наповнення products_rozetka: пріоритет джерела для «Свій / конкурент»

`seller` часто порожній чи ненадійний, тому основне попереднє заповнення колонки «Свій / конкурент» — за тим, **з якої події взято `rozetka_id`**, за пріоритетом (перше джерело, де товар знайдено, і визначає значення):

Кожен ступінь дає пару значень для чернетки — людяне «Джерело» (в таблицю) і «Точність» (число 0-100, фарбує рядок — «Кольори рядків» нижче):

1. **`ad_item_snapshot`** → `Свій`, Джерело «Рекламні кампанії», Точність **100** — реклама завжди по власних товарах.
2. **`product_position_snapshot`** (якщо ще не визначено ступенем 1) → `Свій`, Джерело «Ваш трекер позицій», Точність **70** за замовчуванням — користувачі майже завжди трекають позиції тільки своїх товарів (конкурента там технічно додати можна, але на практиці рідкість).
3. **Той самий товар всередині «своєї» пачки `extra_product_position_snapshot`** — коли `rozetka_id` з `product_position_snapshot` збігається з одним із `rozetka_id` в пов'язаних з ним `extra_product_position_snapshot` того самого сканування (той самий товар природно потрапляє у видачу 1-ї сторінки по своєму ж запиту) → теж `Свій`, Джерело «Ваш товар у видачі (1-а сторінка)», Точність **80**, **не** `Конкурент` за замовчуванням ступеня 4. Без цього кроку власний товар помилково зачитується як конкурент лише тому, що прийшов з extra-події.
4. **Решта `rozetka_id` з `extra_product_position_snapshot`** (не спіймані ступенем 3) → `Конкурент`, Джерело «Конкурент з видачі (1-а сторінка)», Точність **70** за замовчуванням — практично всі рядки цієї події справді конкуренти (подія несе всю 1-у сторінку видачі).
5. **Решта `rozetka_id` з `stock_snapshot`**, ще не класифіковані вище → `Конкурент`, Джерело «Ваш трекер залишків», Точність **50** за замовчуванням (основний сценарій використання — трекати конкурента), але це **найменш надійне джерело**: код не забороняє додати в трекер і власний товар.

Колонка «Джерело» — коротке пояснення саме тим текстом, що вказано вище (можна трохи варіювати формулювання, головне зрозуміло для нетехнічного юзера) — не перелік усіх подій, де товар траплявся, і більше не прив'язане до кольору напряму.

**Конфлікт джерела й продавця — знижує Точність до 20, незалежно від ступеня вище.** Коли `seller` доступний і бізнес-контекст проєкту вже містить перелік власних магазинів (`onboarding.md`, розділ «Свої магазини») — звірити: якщо джерело за пріоритетом вище визначило `Свій`, а `seller` **не входить** у перелік власних магазинів (або навпаки: джерело визначило `Конкурент`, а `seller` **входить**) — це пряма суперечність між двома незалежними сигналами, а не звичайна невпевненість нижчих ступенів. Точний рядок «Свій»/«Конкурент» лишити за пріоритетом джерела вище (людина розбереться сама), Точність знизити до **20**, а саму суперечність описати в колонці «Примітка» (наприклад «Джерело — трекер залишків (Конкурент), але Продавець збігається з вашим магазином X — перевірте»), а не приховувати мовчки.

**Технічна деталь зіставлення ступеня 3:** та сама механіка, що й для «Конкурент для» вище — `search_query` (і бажано `scan_type`) `product_position_snapshot` проти `search_query` в пов'язаних `extra_product_position_snapshot` того самого сканування; `extra_product_position_snapshot` завжди несе всю 1-у сторінку видачі (десь ~60 подій на скан), включно з карткою власного товару, за яким саме й стежили.

## Чого в довідники не кладемо

Все, що вже є в самих подіях: категорія з CRM, виробник, посилання на Rozetka, продавець. Довідник доповнює дані, не дублює їх.

## Рядки ніколи не видаляються

Навіть товар, виведений з асортименту, лишається рядком: звіти за минулі періоди посилаються на його `product_crm_id`, і без рядка вони покажуть голі ID замість назв. Замість видалення — статус «виведено з асортименту».

## Наповнення products_crm: три ступені

Три ступені — **не три паралельні способи знайти товари для таблиці, а каскад заповнення колонки Rozetka ID** для вже визначеного базового набору рядків (усі `product_crm_id` з `order_item_snapshot`, див. вище). Кожен товар пропускається через ступені по черзі, поки Rozetka ID не визначиться.

**Усі три ступені виконуються в одному проході побудови чернетки — ступінь 3 не є опціональним «окремим проходом» на потім.** На практиці траплялось: скіл виконував тільки ступінь 1, а для решти товарів писав у Джерело/Коментар щось на кшталт «кандидата не знайдено ступенями 1-2, потрібне нечітке зіставлення — окремий прохід» — і віддавав чернетку так, ніби це нормальний завершений стан. Це не завершена чернетка, а робота, зроблена на третину: 80% рядків без Rozetka ID через пропущений ступінь 3 — не прийнятний результат для «готової на верифікацію» чернетки. Якщо ступінь 3 справді технічно не вдалось виконати повністю за один виклик (наприклад через обсяг) — це треба прямо сказати користувачу в тексті відповіді («ступінь 3 виконано частково, N зі M товарів») і продовжити, а не мовчки лишати рядки з чужою для читача поміткою «не вдалося зіставити», яка звучить як завершена спроба, а не як «навіть не пробували».

Кожен ступінь дає пару значень для чернетки — людяне «Джерело» (в таблицю) і «Точність» (число 0-100, фарбує рядок — «Кольори рядків» нижче):

1. **Точна зв'язка з `ad_item_snapshot`** — несе `product_crm_id` і `rozetka_id` одночасно, напряму з рекламного кабінету. Джерело «Рекламні кампанії», Точність **100**. Безкоштовно, без помилок, для всього, що було в рекламі. Часто закриває більшу частину асортименту.
2. **Ручне поле `product_crm_id` із подій позицій** — тільки для товарів, не закритих ступенем 1. Користувач може вписати `product_crm_id` сам при додаванні товару в сканер позицій — але якщо він цього не зробив, поле в події все одно присутнє й дорівнює `rozetka_id` (значення за замовчуванням). **Розпізнавання «заповнено вручну» — порівняти `product_crm_id` і `rozetka_id` в тій самій події позицій: різні значення → реальне ручне заповнення, використовувати; однакові → поле не заповнене, пропустити цей ступінь для товару.** Джерело «Вказано вручну в сканері позицій», Точність **100** — це реальний ідентифікатор, введений людиною, не здогадка, настільки ж надійний, як ступінь 1.
3. **Нечітке зіставлення за назвами** — тільки для залишку товарів, яких не покрили ступені 1-2. **Показувати всіх знайдених кандидатів на верифікацію, включно з непевними** — не тільки точний/майже точний збіг. Джерело «Зіставлення за назвою товару», Точність — реальний відсоток збігу назв, якщо алгоритм його рахує, або орієнтир за рівнем впевненості: точний ≈**90**, приблизний ≈**65**, слабкий ≈**40**; рівень впевненості додатково пояснити в «Коментарі», а не мовчки відкидати слабкі збіги, залишаючи в чернетці тільки надійні. **Товари, для яких кандидата взагалі не знайдено (ступінь 3 реально виконано, збігу немає) — Джерело «Не вдалося зіставити», Точність 0.** Не плутати з товаром, для якого ступінь 3 **ще не виконано** (скіл не встиг дійти) — це геть інший стан: писати Джерело «Ступінь 3 не виконано» (теж Точність 0, той самий червоний колір — уваги потребує в обох випадках, але текст чесно каже, чи спроба була). Обидва варіанти все одно лишаються рядком у xlsx (вони вже в базовому наборі — див. вище), просто з порожньою Rozetka ID — і додатково винести їх окремим списком у відповіді користувачу, щоб не загубились серед сотень рядків.

Колонка «Джерело» — коротке пояснення саме тим текстом, що вказано вище (можна трохи варіювати формулювання) — не окремий перелік усіх подій, де товар траплявся, і більше не прив'язане до кольору напряму.

**Тільки третя група вимагає обов'язкової перевірки людиною** — перші дві достовірні за побудовою (обидві дають Точність 100, обидві фарбуються сірим).

**«Посилання на товар» — окремий крок від визначення Rozetka ID, не автоматичний побічний ефект ступеня 1.** `ad_item_snapshot` не несе поля `url`/`href` взагалі (перевірено — його там немає), тож рядок, знайдений через ступінь 1, все одно потребує окремого пошуку: якщо той самий `rozetka_id` траплявся хоч раз у `product_position_snapshot`/`extra_product_position_snapshot` (`url`) чи `stock_snapshot` (`href`), взяти посилання звідти. Якщо `rozetka_id` більше ніде не траплявся — колонка лишається порожньою, **не будувати URL вручну за шаблоном** (немає підтвердженого стабільного формату для всіх категорій).

**«Коротка назва» і «Нормалізована категорія» — брати з будь-якої, не першої-ліпшої події товару.** Окремі події `order_item_snapshot` можуть мати порожні `product_name`/`product_category` (є навіть на не-видалених записах, не тільки на `siq_removed=true`) — а товар зазвичай трапляється в кількох подіях (кожна одиниця — окрема подія). Якщо просто взяти одну довільну/першу подію товару і в ній ці поля порожні — колонка лишиться пустою, хоча в даних значення насправді є. Правильно: перебрати події цього `product_crm_id` (виключивши `siq_removed=true`) і взяти перше непорожнє значення `product_name`/`product_category`, а не зупинятись на першій знайденій події.

**Поріг зняття блоку (див. `core.md`/`onboarding.md`):** таблиця з 0 рядків = блок. Пройти хоча б ступінь 1 (зв'язка з `ad_item_snapshot`) достатньо, щоб зняти жорсткий блок і почати будувати звіти — ступені 2-3 можна дороблювати паралельно, вони не блокують.

## Часове вікно збору чернетки — останні 3 місяці

Запити, якими будується чернетка (усі три ступені `products_crm` з `ad_item_snapshot`/`order_item_snapshot`/позицій, і так само кандидати для `products_rozetka` з `product_position_snapshot`/`extra_product_position_snapshot`/`stock_snapshot`), обмежувати останніми 3 місяцями, а не тягнути всю історію проєкту. Товар, що продавався раніше цього вікна й зник з асортименту, і так ловиться окремо (нижче, «Раз на місяць-два показувати рядки, які довго не траплялись у даних») — не потрібно вантажити всю історію заради нього. Це обмеження стосується тільки побудови/дозаповнення чернетки; звичайні звітні запити користувача (за будь-який період) цим не обмежені.

**Навіть у межах цих 3 місяців — запитувати пакетно, не одним викликом на все вікно.** Інструмент для збору розрізів/агрегатів під каскад — `Run-Query`; обсяг подій за 3 місяці типово вимірюється десятками тисяч (на практиці — 37 705 подій лише по одному типу за період), а сам `Run-Query` попереджає тримати відповідь компактною: короткі періоди (7-30 днів) чи грубіші розрізи, не один запит на весь діапазон. Розбити 3-місячне вікно на послідовні шматки (місяць чи тиждень), виконати `Run-Query` для кожного окремо і об'єднати результати перед тим, як застосовувати три ступені `products_crm`/пріоритети джерела `products_rozetka` — інакше є ризик, що частина товарів мовчки випаде з відповіді через обрізаний результат одного завеликого запиту, а це виглядатиме як «кандидата не знайдено», хоча запит просто не дійшов до цих даних.

## Предзаповнення типу позиції

**Обов'язкова частина того самого проходу побудови чернетки `products_crm`, для кожного рядка — не окрема фіча, яку можна пропустити.** На практиці траплялось, що ця колонка лишалась порожньою в усіх рядках чернетки — так само неприйнятно, як пропущений ступінь 3. Потребує виручки товару за вікно збору (див. «Часове вікно збору чернетки» вище) — це один додатковий агрегат по `product_crm_id`, рахувати його разом з рештою підготовки, не після.

Значення: `Основний товар`, `Подарунок`, `Пакування`, `Послуга`.

Порядок застосування:

1. **Виручка > 0 за період** → `Основний товар`, словник не дивимось узагалі.
2. **Виручка = 0 за період** → застосовуємо словник ключових слів (нижче).
3. **Збігів у словнику немає** → `Основний товар` з позначкою «перевірити».

Ключові слова застосовувати **тільки до позицій з нульовою виручкою** — інакше трапляються хибні спрацювання (реальний товар з схожою назвою чи категорією).

Перевіряти не тільки `product_name`, а й `product_category` — категорія теж може містити слово-маркер (наприклад «коробка» як категорія, а не назва).

**Словник (входження підрядка, нижній регістр):**

- **Подарунок:** `подарунок`, `подарок`, `у подарунок`, `в подарок`, `бонус`, `безкоштовно`, `бесплатно`, `gift`, `промо`, `promo`
- **Пакування:** `коробка`, `коробочка`, `пакування`, `упаковка`, `пакет`, `плівка`, `пленка`, `стрейч`, `скотч`, `наліпка`, `наклейка`, `етикетка`, `этикетка`, `бирка`, `ярлик`, `капсула`, `футляр`, `блістер`, `блистер`, `бульбашков`, `пузырчат`
- **Послуга:** `послуга`, `услуга`, `монтаж`, `установка`, `налаштування`, `настройка`, `гарантія`, `гарантия`, `страхування`, `страховка`, `сертифікат`, `сертификат`, `підписка`, `подписка`, `консультація`, `консультация`

**Додаткова ознака:** позиція, що ніколи не трапляється в замовленні сама (завжди йде довантаженням до іншої позиції того самого `order_internal_id`), — ловить випадки, які нульова виручка пропускає (наприклад безкоштовний супутній товар з ненульовою ціною в чеку).

**Навчання під проєкт:** коли людина виправляє запропонований тип, нове слово дописується в словник **цього проєкту** в business context — далі схожа позиція розмічається сама. Загальний словник вище не чіпати, він спільний для всіх.

## Чернетка вважається завершеною, коли

Перед тим як віддати xlsx користувачу — пройтись по кожному пункту для **кожного** рядка, не тільки для частини:

- Rozetka ID пройшов усі три ступені `products_crm` (не тільки ступінь 1) / усі п'ять пріоритетів `products_rozetka`.
- Тип позиції (`products_crm`) визначено.
- Коротка назва й категорія заповнені там, де вони є хоч в одній події товару (не тільки в першій перевіреній).
- Посилання на товар заповнене там, де `rozetka_id` траплявся в подіях позицій/залишків.

Якщо якийсь пункт технічно не вдалось виконати для всіх рядків за один прохід — **сказати про це прямо в тексті відповіді користувачу** (що саме і скільки рядків не покрито), а не віддавати файл мовчки так, ніби це нормальний завершений стан. Часткова чернетка, подана як повна, — гірше за чесне визнання обмеження.

## Верифікація і підтримання

Перевіряє людина цілком — вона знає свої товари. Впевненість алгоритму потрібна лише щоб відсортувати список: сумнівне — наверх.

**Первинне наповнення → xlsx.** Скачав → перевірив → завантажив назад. За один захід закривається і звірка, і заповнення категорій/типів. Файл віддається заповненим чернеткою, а не порожнім, і будується з готового шаблону (розділ «Шаблон xlsx для верифікації» нижче), а не з нуля.

**Нові товари → завжди з опитуванням.** Автоматично не записувати. Показати всі знайдені дані, щоб людина бачила, що саме запишеться (назва, `product_crm_id`, `rozetka_id`, з якого моменту продається, скільки продажів за тиждень). Якщо товарів декілька — списком, з можливістю позначити потрібні.

### Товар без рядка з'явився під час звичайної роботи (не онбординг, не періодична звірка)

Онбординг (крок 3) пройдено один раз — довідник існує й має рядки. Але асортимент живий: нові `product_crm_id`/`rozetka_id` можуть з'явитись у будь-який момент між сесіями звірки. Це не привід повторно блокувати всю роботу (крок 3 уже пройдено), але й не привід мовчки ігнорувати новий рядок — трактувати так:

- **`products_crm` (звіти по продажах/прибутку).** Товар без рядка **не включати мовчки в підсумок «Основний товар»** — без Типу позиції невідомо, чи це взагалі продаж (може бути `Подарунок`/`Пакування`/`Послуга`), і мовчазне включення повторює саме ту помилку, яку блок кроку 3 мав запобігти. Показати суму/кількість цього товару **окремо** від підтвердженого підсумку, з приміткою «N товару(ів) не в довіднику, на суму X — не враховано в підсумку, потребує перевірки». В **інтерактивному режимі** — одразу в тій самій відповіді (не окремим повідомленням пізніше) запропонувати додати рядок: показати назву, `product_crm_id`, `rozetka_id` (якщо визначається — три ступені з `products_crm`), кількість продажів і суму, і з підтвердженням користувача дозаписати в довідник (`Update-Lookup-Table`, `upsert_rows`, статус «Не перевірено»). У **автоматичному режимі** — не пропонувати (нема в кого запитати дозвіл), тільки перелічити в звіті (`core.md`, «Два режими роботи»).
- **`products_rozetka` (позиції/залишки/конкуренти).** Товар без рядка — типовий, очікуваний стан для конкурента (`core.md`), блокувати чи виключати з розрахунку нічого не треба. Виняток — коли джерело/пріоритет (`ad_item_snapshot`, `product_position_snapshot`) вказує, що це, ймовірно, **свій** товар: тоді так само, як для `products_crm`, в інтерактивному режимі одразу запропонувати додати рядок з підтвердженням, а не лишати «своєю» здогадкою без запису.

**Повна вивантаження і завантаження назад** — механізм на випадок, якщо щось змінилось: назви, категорії, перепривʼязка картки до іншого SKU. Вивантажити всю таблицю в xlsx → людина править → завантажує назад → показати різницю перед застосуванням («змінено N рядків, додано M») → застосувати тільки з підтвердженням.

## Шаблони xlsx для верифікації

Не будувати xlsx з нуля щоразу. Обидва довідники мають свій готовий шаблон з тим самим механізмом верифікації: спадні списки (data validation), умовне форматування — колір рядка автоматично міняється залежно від значення в колонці «Статус». Ніяких реальних товарів у шаблонах немає, тільки generic-приклад на аркуші «Легенда».

- **`products_crm`** → `reference/templates/products_crm-template.xlsx` (ключ у маніфесті — `lookup-template`). Колонки: `product_crm_id` (ключ), `Rozetka ID (перевірити)`, `Джерело` (коротке пояснення для юзера, який ступінь 1-3 визначив Rozetka ID), `Точність (%)` (0-100, фарбує рядок), `Посилання на товар` (`url`/`href` з подій позицій/залишків того самого `rozetka_id`, якщо є — в `ad_item_snapshot` посилання немає), `Коротка назва`, `Нормалізована категорія`, `Тип позиції` (спадний список: Основний товар / Подарунок / Пакування / Послуга), `Статус` (спадний список: Не перевірено / Перевірено / Виведено з асортименту), `Коментар`.
- **`products_rozetka`** → `reference/templates/products_rozetka-template.xlsx` (ключ у маніфесті — `lookup-template-rozetka`). Колонки: `rozetka_id` (ключ), `Джерело` (коротке пояснення для юзера, яка подія визначила «Свій/конкурент» — див. схему вище), `Точність (%)` (0-100, фарбує рядок), `Назва картки`, `Посилання на товар` (`url` або `href` залежно від джерела), `Продавець`, `Свій / конкурент` (спадний список: Свій / Конкурент), `Конкурент для (rozetka_id свого товару)` (текст, можливо кілька значень через кому — див. схему вище), `Нормалізована категорія`, `Статус` (спадний список: Не перевірено / Перевірено / Неактуально), `Примітка`.

## Кольори рядків: світлофор уваги

Кольори автоматичні (умовне форматування, вже налаштоване в обох шаблонах на колонки «Статус» + «Точність (%)») — нічого фарбувати вручну не потрібно. «Джерело» — тільки текст для людини, на колір не впливає, саме «Точність» його визначає. Мета не просто позначити стан, а розподілити увагу людини: де можна пробігтись побіжно, а де розібратись уважно. Перше правило зверху, що спрацювало для рядка, — те й визначає колір, решта не перевіряються:

1. **Зелений** — Статус = «Перевірено». Людина підтвердила рядок, найвищий пріоритет завжди, незалежно від Точності.
2. **Лаванда** — Статус = «Виведено з асортименту» (`products_crm`) / «Неактуально» (`products_rozetka`). Архівний стан, окремий від шкали точності нижче.
3. **Червоний** — Точність < 50. Не вдалось зіставити товар узагалі (`products_crm`, Точність 0) або конфлікт джерела з продавцем (`products_rozetka`, Точність 20) — максимум уваги.
4. **Сірий** — Точність ≥ 90. Ступінь 1-2 в `products_crm` (обидва по побудові надійні) чи `ad_item_snapshot` у `products_rozetka` — можна не перевіряти детально.
5. **Жовтий** — Точність 50-89 (за замовчуванням для решти рядків зі статусом «Не перевірено») — ймовірно вірно, варто глянути побіжно.

**Процес заповнення (однаковий для обох):**
1. Завантажити відповідний шаблон через `curl` як звичайний довідковий файл (маніфест, ключі `lookup-template`/`lookup-template-rozetka`).
2. Дозаписати рядки чернетки (каскад трьох ступенів — вище для `products_crm`; пріоритет джерела для `products_rozetka` — теж вище) починаючи з рядка 2 — **у сам шаблон**, зберігаючи форматування й спадні списки, не створюючи xlsx з нуля.
3. **Статус кожного нового рядка — завжди `Не перевірено`.** Скіл ніколи не проставляє «Перевірено» сам, навіть якщо впевнений у значенні (наприклад ступінь 1 для `products_crm` — зв'язка з `ad_item_snapshot`) — це виключно рішення людини. Помилка в інший бік (проставити «Перевірено» самому) вже траплялась на практиці й підриває сенс верифікації.
4. Аркуш «Легенда» лишити як є (generic-текст із шаблону) — не редагувати під конкретний проєкт. Пояснення нестандартних евристик конкретного проєкту (наприклад, «в проєкті немає `ad_item_snapshot`, Rozetka ID — здогадка за форматом ID») писати в колонку «Коментар»/«Примітка» відповідних рядків, а не переписувати легенду.
5. Віддати готовий файл користувачу на перевірку.

**Технічно:** файли — стандартний `.xlsx` (OOXML). Редагувати програмно зручно через `openpyxl` (Python): `load_workbook(template_path)`, дозаписати значення в комірки з рядка 2 (не через `ws.append`, якщо потрібно зберегти рядок 1 з фільтром недоторканим), зберегти під новим ім'ям. Спадні списки й умовне форматування вже прописані в обох шаблонах на діапазон до рядка 2000 — переналаштовувати нічого не потрібно, досить заповнити комірки.

**Видалення рядків з файлу не застосовується.** Якщо рядок зник із файлу — це, швидше за все, випадковість, а не намір видалити. Для виведення з асортименту є статус, а не видалення.

## Правила

- **Існуючі рядки скіл ніколи не переписує сам.** Тільки через явне завантаження файлу людиною.
- **Статус ставить тільки людина.** Нові рядки завжди приходять неперевіреними.
- **Групи один-до-багатьох підсвічувати явно.** Якщо кілька рядків `products_crm` ведуть на одну картку Rozetka — показати це прямо, інакше людина сприйме їх за дублікати.
- **Раз на місяць-два** показувати рядки, які довго не траплялись у даних. Не видаляти, тільки показати.

## Межі запису

**Підготовка чернетки дозволу не потребує** — запити до `ad_item_snapshot`/позицій, нечітке зіставлення за назвами, збірка xlsx-чернетки — це читання й обчислення, робити одразу, не питаючи «можна почати». Дозволу вимагає тільки сам запис у Mixpanel, і питати треба з готовою чернеткою в руках (конкретні числа й приклад рядків), а не заздалегідь.

Кожного разу окреме явне підтвердження **перед записом**:
- Створення lookup table (довідника ще нема) — `Create-Lookup-Table`.
- Додавання/дозаписування рядків до вже існуючого довідника (з показом даних) — `Update-Lookup-Table` (`upsert_rows`) — дельта, не повний перезапис, чужі рядки не чіпає.
- Застосування завантаженого xlsx (з показом diff) — теж `Update-Lookup-Table` (`upsert_rows`/`delete_keys`, залежно від diff).

## Технічні особливості Mixpanel lookup tables

Перевірено на практиці — тримати в голові при роботі з `Update-Lookup-Table` (`upsert_rows`) і `Get-Lookup-Table`:

- До 10 000 рядків у таблиці.
- Дельта-оновлення (`upsert_rows`) працює: патчаться тільки передані колонки, решта зберігається.
- **Переімпорт займає понад десять хвилин.** Одразу після запису читати таблицю безглуздо — свіжих даних ще не буде.
- **`change_summary` і `last_modified_at` не показники успіху.** Перший рапортує про прийняття запиту негайно, другий оновлюється в момент виклику, а не після фактичного застосування. Перевіряти за реальним вмістом і `row_count`, а не за цими полями.
- Числові значення приводяться до float: записав `"552581958"` рядком — прочитається `552581958.0`.
- Ім'я ключової колонки не зберігається як задане — читається просто як `Primary Key`.
- Порожні значення випадають із рядка при записі.
- **`Get-Lookup-Table` віддає прев'ю з лімітом, а не всю таблицю.** Точний потіл ліміту не перевірений — якщо він низький, механізм «скачав-поправив-залив» на великому асортименті через API поверне неповні дані. Для повної вивантаження про запас орієнтуватись на реальний `row_count`, а не вважати відповідь повною автоматично.
- **Прив'язка таблиці до властивості — тільки вручну в Lexicon**, інтерфейс Mixpanel. Без цього кроку таблиця лежить мертвим вантажем і не підтягується автоматично в аналітику. Підказати користувачу зробити це на онбордингу (див. `onboarding.md`).
- Видалення таблиці через MCP неможливе — тільки через інтерфейс Mixpanel.
