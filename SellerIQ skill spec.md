# Спецификация скила SellerIQ

Свод договорённостей для реализации. Составлено 26 июля 2026 по итогам разбора на реальных данных проектов ACG_Prod и ART planet.

---

## 1. Назначение

Скил не готовит стандартный отчёт. Его задача — дать ассистенту точное понимание схемы данных SellerIQ, чтобы пользователь мог строить **любые** отчёты и разрезы под свой бизнес: удержание клиентов, процент выкупа, сравнение с конкурентами, эффективность менеджеров, что угодно.

Отчёт — частный случай, а не цель.

---

## 2. Распространение

Открытый репозиторий на GitHub. Пользователь загружает себе только `SKILL.md`, остальное подтягивается по ссылкам на `raw.githubusercontent.com`.

```
selleriq-claude-skill/
  README.md                      ← инструкция по установке
  skill/
    SKILL.md                     ← это ставит пользователь
  reference/
    index.json                   ← манифест: версия, дата, список файлов
    core.md                      ← ловушки трактовки
    order-item-snapshot.md
    product-position-snapshot.md
    ad-item-snapshot.md
    stock-snapshot.md
    extra-product-position-snapshot.md
    lookup-tables.md
    onboarding.md
    recipes.md
```

Ссылки в манифесте ведут на ветку `main`, а не на конкретный коммит — тогда правка подхватывается сама. Кеш raw-файлов около пяти минут.


Поле `when` — главное: по нему определяется, что тянуть, и не грузится лишнее.

### Гибрид: что в скиле, что на GitHub

| | В скиле | На GitHub |
|---|---|---|
| Сеть | не нужна | нужна |
| Веб-доступ у пользователя | не нужен | должен быть включён |
| Скорость | мгновенно | задержка запроса |
| Обновление | переустановка | сразу у всех |

**В `SKILL.md`** — то, что меняется редко и без чего ответ будет неверным: ловушки трактовки, базовая семантика. Дублируется намеренно, чтобы при недоступном GitHub скил не врал, а работал на минимуме и предупреждал об этом.

**На GitHub** — часто правимое: рецепты, описания новых полей, онбординг.

Переустановка нужна только когда меняется сам `SKILL.md`.

### Публичность

Репозиторий открытый — семантика событий и логика работы видны всем. Для документации, которая и так открыта, разницы нет. Но если в `recipes.md` попадут неочевидные приёмы анализа, это часть ценности продукта — стоит решить, всё ли туда класть.

### Дробить на несколько скилов не нужно

Разные скилы — разные установки, и выбор между ними делается по описаниям, то есть с риском ошибки. Один скил с файлами внутри надёжнее: какой файл читать, определяет инструкция, а не догадка о релевантности.

## 3. Как это грузится в контекст

Три уровня:

1. **Всегда** — только имя и описание скила, несколько десятков токенов
2. **При срабатывании** — тело `SKILL.md` целиком
3. **По необходимости** — справочные файлы, каждый только когда до него дошло дело

Прочитанное остаётся в контексте до конца разговора; в новом разговоре читается заново. Ничего не сохраняется на стороне пользователя.

Практические следствия:

- `core.md` держать коротким — он грузится всегда
- справочники дробить мельче, чтобы вопрос про рекламу не тянул описание остатков
- `SKILL.md` ориентировочно до 500 строк
- в инструкции явно разрешить **не** грузить справочники, когда они не нужны

Порядок величин: манифест плюс `core` плюс один-два справочника — около трёх тысяч токенов на разговор. На фоне ответов Mixpanel это незаметно.

## 4. Устойчивость к будущим доработкам

Скил у пользователей будет отставать от того, что добавляется в события. Чтобы это не ломалось:

**Определять возможности по факту, а не по версии.** Формулировка: «если поле `order_status_group` присутствует — использовать его; если нет — спросить у пользователя». Тогда в день, когда оно появится, старый скил подхватит его сам.

**Формулировать списки полей как открытые.** Не «вот все поля события», а «вот известные на момент версии X; встретил незнакомое — посмотри значения и действуй по смыслу».

**Источник истины — данные, документация лишь подсказка.**

**`schema_v`** ~~уже передаётся в `product_position_snapshot`. Стоит добавить и в остальные события.~~ **Проверено по коду 26.07.2026: уже присутствует во всех пяти событиях** (`order_item_snapshot`, `product_position_snapshot`, `extra_product_position_snapshot`, `ad_item_snapshot`, `stock_snapshot`). Пункт закрыт, ничего доделывать не нужно — сохранён как пример того, как быстро код обгоняет документацию.

## 5. Что где хранится

| Что | Где | Почему там |
|---|---|---|
| Семантика событий, ловушки, рецепты | GitHub + дубль ловушек в `SKILL.md` | одинаково у всех, обновляется без участия пользователя |
| Конфиг и приоритеты магазина | business context **проекта** | своё у каждого, читается автоматически |
| Справочник товаров | lookup table `products_crm` | объёмные данные |
| Справочник карточек | lookup table `products_rozetka` | объёмные данные |

**Контекст организации не используется.** Раньше планировалось дублировать туда семантику как страховку на случай, если скил не сработает. Отказались: человек ставит скил специально ради SellerIQ, он сработает. А копия в контексте у каждого пользователя была бы неуправляемой — обновить её централизованно невозможно.

## 6. События: что покрывает каждое

| Событие | Чьи товары | Ключ товара |
|---|---|---|
| `order_item_snapshot` | только свои | `product_crm_id` |
| `ad_item_snapshot` | только свои | `product_crm_id` **и** `rozetka_id` |
| `product_position_snapshot` | свои и конкуренты | `rozetka_id` |
| `extra_product_position_snapshot` | конкуренты с 1-й страницы | `rozetka_id` |
| `stock_snapshot` | свои и конкуренты | `rozetka_id` |

Товар без строки в справочнике в позициях или остатках — скорее всего конкурент, а не ошибка.

`ad_item_snapshot` несёт оба идентификатора сразу — это готовая достоверная связка CRM ↔ Rozetka без сопоставления по названиям.

## 7. Правила трактовки

Ядро ценности скила. Одинаковы у всех пользователей.

### product_position_snapshot

- **Обе позиции равны нулю** (`organic_global_pos` и `ad_global_pos`) → товара нет на отсканированных страницах. Это не ошибка сканера.
- **Средние позиции считать только по ненулевым значениям.** Иначе нули занижают результат. На ACG за 25.07 разница вышла существенной: 18,9 против 22,4 в органике и 30,9 против 50,0 в рекламе.
- **`group_source`**: `DIRECT` — позиция найдена напрямую; `GROUP` — взята от другого цвета в группе; `NONE` — товар не найден в выдаче.
- **`group`** (boolean) — отдельное поле, означает наличие цветовой группы. Не путать с `group_source`.
- **A/B-варианты выдачи.** Rozetka показывает разным пользователям разные варианты. Поля с суффиксами `_0`, `_1`, `_3`, `_4`; поле без суффикса — среднее по доступным.
  *Документация описывает суффиксы только для `serp_*`. Проверено по коду 26.07.2026: суффиксы реально генерируются и для `organic_page/pos_on_page/global_pos` и `ad_page/pos_on_page/global_pos` — подтверждено, не только гипотеза.*
  *Доступность бакетов зависит от тарифа (`ROZETKA_AB_FULL_BUCKETS` = все 4, `MIN` = только `_0`), но на 26.07.2026 у всех действующих тарифов включён полный набор — код на «однобакетный» режим есть, но сейчас не используется ни одним планом. Не полагаться на то, что `_1/_3/_4` всегда будут у всех: механизм ограничения по тарифу существует и может включиться.*
- **`label`** — произвольная метка товара, смысл задаёт пользователь. Полагаться нельзя: в ACG там `default` и `info`, то есть даже автор соглашения им не пользуется.
- **`Event Props`** — произвольные пары ключ-значение, задаются при добавлении товара в сканер, попадают во все события этого товара и запроса. Туда кладут бренд, категорию, поставщика, артикул.
  *Не до конца проверено: есть признак, что при отправке в событие ключи получают префикс `user__` (например `article` → `user__article`), хотя ни доки, ни бизнес-контекст Mixpanel это не показывают — примеры везде дают ключ как есть. Проверить на реальном событии перед тем, как писать в reference-файл как факт.*
- **`seller`** — продавец карточки. Заполнен, даёт определение «свой/чужой» напрямую.
- **`url`** — прямая ссылка на товар. Строить не нужно.
- **`scan_type`** — `search` или `category`.
- **`product_crm_id`** здесь задаётся пользователем вручную при добавлении товара. Может быть пустым, произвольным или дублировать `rozetka_id` — в ACG именно так.

### order_item_snapshot

- **Одно событие = одна единица товара.** `quantity` всегда 1. Заказ из трёх штук даёт три события.
- **События с пустыми `product_name`, `order_status_name` и `sales_channel` одновременно** — похоже на артефакты дедупликации при замене товара в заказе или задержке подтягивания SKU.
  *Проверено по коду 26.07.2026: явного правила/фильтра под эти три поля одновременно в бэкенде нет — это эмпирическое наблюдение с ACG, а не гарантированная механика. В reference писать как «похоже на», не как факт; из подсчётов по-прежнему разумно исключать.*
- **`ad_cost` входит в `product_net_profit_amount`.** Но если товар в заказе заменён и связь по external ID теряется — реклама не подтягивается. Для ДРР надёжнее суточный расход из `ad_item_snapshot`. На ACG 25.07: 1 190 ₴ за сутки против 556 ₴, отнесённых к продажам.
  *Уточнение по коду: аллокация рекламных расходов идёт по доле выручки товара внутри товарной группы заказа, а не по всему заказу целиком.*
- **Рекламные поля масштабированы** на долю выручки товара в заказе → `SUM` даёт корректные итоги.
- **`is_ad`** = `utm_campaign=Rozetka` и `utm_medium=cpc`. *Подтверждено кодом дословно.*
- **Доставка** считается на уровне заказа и распределяется между товарами пропорционально их стоимости. *Подтверждено кодом; та же пропорция применяется и к сумме постоплаты (`delivery_postpay_sum`) — в исходной спеке этого не было.*
- **Директивы `@siq`** в комментарии к заказу — дополнительные расходы, доходы и произвольные параметры. Расходы и доходы уже учтены в чистой прибыли. Override базовых значений — полный список по коду: `price`, `costPrice`, `commission`, `percentCommission`, `discount`, `percentDiscount` (для товара), `shipping_costs` (для заказа). *В исходной спеке не хватало `percentCommission` и `percentDiscount`.*
- **`product_category` и `product_manufacturer` приходят из CRM**, но качество низкое: в ACG 40 значений, среди них `Товари для кухні` и `Товар для кухні` как разные, а также названия товаров вместо категорий и `коробка` как категория. Отсюда потребность в нормализованной категории в справочнике.
- **Идентификаторы заказа:** `order_internal_id` (CRM) и `order_external_id` (Rozetka, Prom).

### ad_item_snapshot — ~~три~~ **четыре горизонта**

*Проверено по коду 26.07.2026 (`rztkAdStats.service.js`, `mpSchema.js`): горизонтов четыре, не три — в исходной спеке пропущен агрегат по кампании целиком.*

| Префикс | Период | На какой вопрос отвечает |
|---|---|---|
| `rztk_ad_daily_*` | сутки | куда ушли деньги вчера |
| `rztk_ad_since_last_order_*` | с последнего заказа | что сломалось прямо сейчас |
| `rztk_ad_item_*` | всё время, по этому размещению/товару | окупается ли товар в принципе |
| `rztk_ad_campaign_*` | всё время, по кампании целиком | окупается ли кампания в целом (**новое, было пропущено**) |

Каждая группа несёт одинаковый набор из 9 метрик: `_money`, `_clicks`, `_views`, `_transactions`, `_cpc`, `_cpo`, `_ctr`, `_cvr`, `_cr` (у `since_last_order` — 9 без отдельного `_views`→ те же 9, но без изменений в наборе). Формулы: `cpc=money/clicks`, `cpo=money/transactions`, `ctr=clicks/views*100`, `cvr=transactions/views*100`, `cr=transactions/clicks*100`, всё `null` при делении на 0.

**`rztk_ad_since_last_order_*` присутствует не всегда** — только когда `transactions с последнего заказа > 0`. На дни без заказов этих 9 полей просто нет в событии (не 0 — отсутствуют). Сбрасывается на день **после** дня с заказом, не внутри того же дня.

Второй горизонт важнее прочих для ежедневной работы: он ловит сломавшуюся кампанию раньше остальных. Пример с ACG: «Магнітний конструктор Minecraft» — 615,94 ₴ с последнего заказа, 122 клика, 2 продажи, CPO 308 ₴ при цене товара около 859 ₴. За всё время CPO у него 131 ₴, то есть кампания деградировала именно сейчас.

**Событие не шлётся, если за день нет изменений** (`hasOrders`/дельта = 0 по всем метрикам) — «нет события за день» означает «без активности», а не «активность нулевая записана явно». Первый синк размещения тоже не шлёт событие (это baseline).

`product_crm_id` и `rozetka_id` в этом событии — это собственные идентификаторы Rozetka ad-cabinet API (`price_offer_id` и `item_id`), а не эвристическое сопоставление — самая надёжная связка CRM↔Rozetka из всех источников.

### stock_snapshot

Ключ `rozetka_id`. Поля: `name`, `href`, `img`, `seller`, `top_label`, `prev_stock_limit`, `stock_limit`, `sales_count`, `restock_count`, цены и данные карточки, плюс не описанные в документации `scan_time`, `scan_is_exact`, `scan_limit_reason`. Позволяет считать скорость продаж и оценивать конкурентов.

**`stock_change_type`** (раздел 17, открытый вопрос закрыт проверкой кода 26.07.2026): поле существует, задаётся сравнением текущего и предыдущего остатка. Значения (нижний регистр!), реально доходящие до Mixpanel: `out_of_stock`, `restock`, `stock_decrease_adjustment` (защита от ложного всплеска продаж при ручной перезаливке остатка — сработает при просадке больше ~20 единиц за скан), `sale`. Значения `no_change`/`unknown` в коде есть, но до Mixpanel не доходят — событие шлётся только при `changed=true`.
⚠️ И документация `seller.iq`, и org-level business context Mixpanel ссылаются на `RESTOCK` в верхнем регистре — это ошибка в документации, реальное значение `restock` строчными.

### Статусы заказов

Пользователи заводят статусы сами, названия и смысл различаются. У одних «Фуллфилмент» — это фулфилмент Rozetka, у других сторонний склад.

**Группировки статусов в событии сейчас нет.** В SalesDrive она существует (в работе / выполнено и оплачено / отменено), но SellerIQ её не передаёт.

**Проверено по коду 26.07.2026 — гипотеза о стандартных ID 1-7 не подтвердилась.** В бэкенде нет никакого хардкода или seed-списка статусов: `order_status_id`/`order_status_name` идут как есть из метаданных CRM-аккаунта пользователя, полностью произвольны и специфичны для аккаунта. Таблица ниже (наблюдение по ACG от 25.07) оставлена как иллюстрация, но **не как правило**: сверка на ART planet (тестовые данные, не показатель, но заметно) дала другую раскладку тех же ID — например `12` там означает «Недозвон», а «Фулфілмент» — `13` (у ACG наоборот: `12`=Фуллфілмент). Даже низкие ID не гарантированно совпадают по смыслу между аккаунтами.

**Вывод для скила: ID статусов никогда не зашивать.** Всегда получать список фактическим breakdown по `order_status_id`/`order_status_name` за период в конкретном проекте и спрашивать пользователя, что есть что (см. раздел 8 «Принцип опроса»).

| ID | Название (ACG, для примера) | Похоже на |
|---|---|---|
| 1 | Новий | стандартный |
| 2 | Повторний дзвінок | стандартный |
| 3 | На відправку | стандартный |
| 4 | Відправлено | стандартный |
| 5 | Продаж | стандартный |
| 6 | Відмова | стандартный |
| 7 | Повернення | стандартный |
| 10 | Обробляється менеджером | кастомный |
| 12 | Фуллфилмент | кастомный |
| 13 | Прибув | кастомный |
| 18 | Очікує оплату | кастомный |

**Есть готовый строительный блок для будущей группировки**, которым SellerIQ пока не пользуется: SalesDrive API отдаёт по каждому статусу признак `type=2 && active=1` (по метаданным аккаунта) — это бинарный флаг «закрытый / не закрытый» статус. Сейчас используется backend'ом только для выбора диапазона синхронизации, в `order_item_snapshot` не пробрасывается. Даёт только 2 группы (закрыт/не закрыт), а не 3 (продажа/отказ/в процессе) — «успех» и «отмена» этим флагом не различить. См. раздел 18.

`order_type_id` — это **не** группа статуса, а источник заказа: `1` — «Заявка он-лайн», `3` — «Введено вручну».

### Защита чужого содержимого

Business context перезаписывается целиком, слияния нет. Скил владеет только своим блоком между маркерами: читает контекст, находит блок, заменяет только его, остальное переносит без изменений.

### Принцип опроса

## 9. Справочники

### products_crm — ключ `product_crm_id`

Цепляется к заказам и рекламе.

| Колонка | Кто заполняет |
|---|---|
| `product_crm_id` — ключ | из данных |
| Rozetka ID | из `ad_item_snapshot` или сопоставления |
| Коротка назва | заготовка из данных, человек правит |
| Нормалізована категорія | человек |
| Тип позиції | человек, догадка предзаполнена |
| Статус | человек: перевірено / не перевірено / виведено з асортименту |
| Посилання CRM | по шаблону из конфига |

Ключ — `product_crm_id`, потому что он уникален и **неизменен**. Одна карточка Rozetka может соответствовать нескольким товарам в CRM (разные поставщики) — тогда `rozetka_id` просто повторяется в обычной колонке.

Если карточку перепривязали к другому SKU — меняется одна ячейка `Rozetka ID`, ключ остаётся, ручная работа не теряется.

### products_rozetka — ключ `rozetka_id`

Цепляется к позициям и остаткам, включая конкурентов.

| Колонка | Кто заполняет |
|---|---|
| `rozetka_id` — ключ | из данных |
| Назва картки | из `name` |
| Продавець | из `seller` |
| Свій / конкурент | предзаполняется по `seller`, подтверждает человек |
| Нормалізована категорія | человек, по желанию |
| Примітка | человек, по желанию |

Колонка «свій / конкурент» нужна как страховка: у части пользователей `seller` может быть пустым или ненадёжным. Места не занимает, при необходимости пригодится.

Создаётся не на первом запуске, а когда впервые появятся события позиций.

### Что в справочники не кладём

Всё, что есть в событиях: категория из CRM, производитель, ссылка на Rozetka, продавец.

### Строки не удаляются никогда

Даже выведенный из ассортимента товар остаётся: отчёты за прошлые периоды ссылаются на его `product_crm_id`, и без строки они покажут голые ID. Вместо удаления — статус «виведено з асортименту».

## 10. Наполнение справочника: три ступени

1. **Точная связка из `ad_item_snapshot`** — бесплатно, без ошибок, для всего что было в рекламе. На ACG закрыло бы больше половины ассортимента.
2. **Настоящий `product_crm_id` из позиций** — если пользователь его заполнил.
3. **Нечёткое сопоставление по названиям** — только для остатка. На ACG дало около 85% уверенных попаданий из 52 товаров.

Только третья группа требует обязательной проверки.

## 11. Предзаполнение типа позиции

Значения: `Основний товар`, `Подарунок`, `Пакування`, `Послуга`.

### Порядок

1. **Выручка > 0** → `Основний товар`, словарь не смотрим
2. **Выручка = 0 за период** → применяем словарь
3. **Совпадений нет** → `Основний товар` с пометкой «перевірити»

Ключевые слова применяются **только к позициям с нулевой выручкой** — иначе ложные срабатывания. У ACG «Сіль Артемсіль 10 кг … мішок» даёт 243 357 ₴, «Чохол для ножа» — реальный товар, «Ліцензія Minecraft» — 12 490 ₴.

### Словарь (вхождение подстроки, нижний регистр)

**Подарунок:** `подарунок`, `подарок`, `у подарунок`, `в подарок`, `бонус`, `безкоштовно`, `бесплатно`, `gift`, `промо`, `promo`

**Пакування:** `коробка`, `коробочка`, `пакування`, `упаковка`, `пакет`, `плівка`, `пленка`, `стрейч`, `скотч`, `наліпка`, `наклейка`, `етикетка`, `этикетка`, `бирка`, `ярлик`, `капсула`, `футляр`, `блістер`, `блистер`, `бульбашков`, `пузырчат`

**Послуга:** `послуга`, `услуга`, `монтаж`, `установка`, `налаштування`, `настройка`, `гарантія`, `гарантия`, `страхування`, `страховка`, `сертифікат`, `сертификат`, `підписка`, `подписка`, `консультація`, `консультация`

Проверять не только `product_name`, но и `product_category` — в ACG встречается категория `коробка`.

### Дополнительный признак

**Позиция никогда не встречается в заказе одна.** Доступно через `order_internal_id`. Подарок и упаковка всегда идут в довесок. Ловит случаи, которые нулевая выручка пропускает — например «Капсула для монет» с ценой 69 ₴.

### Обучение под проект

Когда человек исправляет предложенный тип, слово дописывается в словарь проекта в business context. В следующий раз похожая позиция разметится сама.

## 12. Верификация и поддержание

Проверяет человек целиком — он знает свои товары. Уверенность алгоритма нужна только чтобы отсортировать список: сомнительное наверх.

### Первичное наполнение → xlsx

Скачал, проверил, загрузил обратно. За один заход закрывается и сверка, и заполнение категорий и типов. Гиперссылки на товар прямо в файле. Файл отдаётся заполненным черновиком, а не пустым.

### Новые товары → всегда с опросом

Автоматически не записывать. Показывать все найденные данные, чтобы человек видел, что именно запишется:

> Появился товар, которого нет в справочнике:
> **Насадки для зубної щітки Oral-B EB 17 X** · CRM `583358791` · Rozetka `583358791`
> Продаётся с 19.07, за неделю 100 продаж.
> Записать в справочник?

Если товаров несколько — списком, с возможностью отметить нужные.

### Полная выгрузка и загрузка обратно

Механизм на случай, если что-то изменилось: названия, категории, перепривязка карточки к другому SKU.

Выгружаю всю таблицу в xlsx → человек правит → загружает обратно → показываю разницу перед применением:

> Изменений: 4 строки изменены, 2 добавлены.
> Применить?

Удаление не применяется: если строка пропала из файла, скорее всего это случайность. Для вывода из ассортимента — статус, а не удаление.

### Правила

- **Существующие строки скил не переписывает никогда.** Только через явную загрузку файла человеком.
- **Статус ставит только человек.** Новые строки всегда приходят непроверенными.
- **Группы один-ко-многим подсвечивать.** Если три строки ведут на одну карточку Rozetka — показать явно, иначе человек примет их за дубликаты.
- **Раз в месяц-другой** показывать строки, не встречавшиеся в данных долгое время. Не удалять, только показать.

## 13. Границы записи

Требуют явного разрешения:

- **Business context** — каждый раз. Запись полная, слияния нет, там может быть чужое содержимое. Заодно проверка, что смысл понят верно.
- **Создание lookup table** — обязательно.
- **Добавление новых строк** — каждый раз, с показом данных.
- **Применение загруженного xlsx** — с показом разницы.

Без разрешения скил только читает.

## 15. Два режима работы

**Интерактивный.** Человек рядом, можно уточнить, показать кнопки, попросить проверить. Все механики онбординга и верификации рассчитаны на него.

**Автоматический** — регулярный запуск по расписанию. Спросить некого: задача выполняется в отдельной сессии, контекст исходного разговора не переносится, остановиться и задать вопрос она не может.

Что доступно автоматическому запуску: скил, коннекторы, business context, lookup tables. Что недоступно: переписка.

Отсюда:

- шаблон отчёта, о котором договорились в разговоре, надо **записать** в business context проекта
- в автоматическом режиме не задавать вопросов — строить на том, что есть, и писать об ограничениях в самом отчёте
- новые товары в автоматическом режиме не записывать, а перечислить в отчёте

## 16. Технические особенности Mixpanel MCP

Проверено на практике.

### Регионы

Проект и коннектор должны совпадать: `mcp.mixpanel.com` для US, `mcp-eu.mixpanel.com` для EU. Иначе отказ. Проверять первым шагом онбординга.

### Business context

- Уровни `project` и `organization`; `Get-Business-Context` с `project_id` возвращает оба
- Запись — полная замена, слияния нет
- Документированного лимита размера найти не удалось

### Lookup tables

- До 10 000 строк
- Дельта-обновление (`upsert_rows`) работает: патчатся только переданные колонки, остальные сохраняются
- **Переимпорт занимает больше десяти минут.** Сразу после записи читать бессмысленно
- **`change_summary` и `last_modified_at` не показатели** — первый рапортует об успехе немедленно, второй обновляется в момент вызова. Проверять по содержимому и `row_count`
- Числовые значения приводятся к float: записал `"552581958"`, читается `552581958.0`
- Имя ключевой колонки не сохраняется, читается как `Primary Key`
- Пустые значения выпадают из строки
- `Get-Lookup-Table` отдаёт превью с лимитом, а не всю таблицу
- **Привязка таблицы к свойству — только вручную в Lexicon.** Без неё таблица лежит мёртвым грузом
- Удаление таблицы через MCP невозможно
